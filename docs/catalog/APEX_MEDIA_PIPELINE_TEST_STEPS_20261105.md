# Apex Track 1 — Product image acceptance and test runbook

**November 5, 2026.** Applies to verified [PR #281](https://github.com/zanibethel/apex/pull/281) only after exact-head CI passes, the SQL migration is applied, and the Edge worker is deployed. Supabase project `fhqpkpztercadcxspdkg`; domain `apexanabolics.co`.

## Delivered system components

- Dedicated **private** approved-copy storage bucket (`apex-approved-product-images-v1`), separate from the unchanged **private** supplier source bucket (`apex-draft-product-images`).
- `apex_media_issue_preflight_v1`, `apex_media_issue_v1`, `apex_media_resolve_v1`, `apex_media_revoke_v1`: all service-role-only RPCs. Anonymous and ordinary authenticated users have **no direct access**. Issuance requires a current internally approved product-review snapshot, the **latest** recorded identity and image-use-rights evidence, valid independent supplier and product authorizations, no identity/admin hold, and exact product image, category, name, SKU and description. The final SQL insert repeats this check under a product-row lock.
- Supabase Edge `apex-media-v1`, with JWT verification handled explicitly for privileged POSTs using Auth `getUser`, trusted `app_metadata.apex_role`, confirmed email and the authenticated admin. Supabase supplies the Edge service-role credential internally; **never** configure a service-role key in Vercel/browser. POST issue verifies exact private image file signature, hashes source bytes with SHA-256, copies to a private immutable key, downloads the copy, rehashes and only then inserts the version. Failed finalization may leave an inaccessible private orphan (never public).
- GET delivery checks the **two OFF-by-default database gates** and current product/review/evidence/version/authorization/hold state on each request, downloads the latest unrevoked private copy, rehashes bytes, streams only PNG/JPEG/WebP with `no-store`, and never returns a private source path or signed URL. Next proxies it through `/api/catalog/media/v1/<product-uuid>`. Approved product cards and detail pages use this URL with a safe graphic fallback.
- Admin product media panel supports **Create reviewed image version** only with current internal approval + recorded latest evidence, and **Revoke most recent version**. A revoke cannot be undone. The product/edit/approval triggers from PR #276 also permanently revoke old versions.

## Step-by-step operator test (production release remains OFF)

1. **Unauthorized browser test.** In a logged-out private window open [the catalog](https://apexanabolics.co/catalog). Existing unapproved products must **not** appear. Directly request `https://apexanabolics.co/api/catalog/media/v1/00000000-0000-4000-8000-000000000001` — expected **404** with `{"state":"unavailable"}`. Do not expect a product photo until both reviewed release gates are separately activated.
2. **Supplier review.** Sign in as an authorized supplier owner/manager at `https://apexanabolics.co/supplier/sign-in`, then open [Product image readiness](https://apexanabolics.co/supplier/catalog/media-readiness). View **All products**, then **Needs action**, **Identity holds**, **Image issues** and **Review queue**. Inspect each photograph, exact strength/identity, ownership and evidence. The 13 held/uncategorized records must **not** be guessed or approved. Verify filter counts and responsive cards on a phone.
3. **Complete a legitimately verifiable draft.** In the [supplier product editor](https://apexanabolics.co/supplier/catalog), set accurate details and product-specific, licensed or owned image, and complete the private eight-step setup. Explicitly **Submit for internal review**. It should appear as pending; a duplicate request should not create a second pending submission. Do **not** fabricate approvals to force this test.
4. **Independent admin content review.** Sign in as trusted platform admin at `https://apexanabolics.co/admin/sign-in`, open [Product Reviews](https://apexanabolics.co/admin/product-reviews), inspect the exact review submission/photo and approve only if the evidence supports it. Supplier changes/new photos must invalidate the old review.
5. **Independent image proof.** In [Admin image release readiness](https://apexanabolics.co/admin/media-readiness?queue=evidence), select an internally approved submission, provide the exact product identity source and **rights to reproduce this image** references, then record `evidence_recorded`. Both references must be substantive (not placeholder notes), and the record must correspond to the current private image path. A newer correction entry invalidates older proof.
6. **Verified seller/product release authorization.** The independent seller and individual product authorization records must be valid, reviewed, current, and unexpired; a supplier Publish toggle is insufficient. The [Admin catalog release screen](https://apexanabolics.co/admin/catalog-release) is **read-only** and identifies missing gates. If authorization is missing, version issuance MUST report that it did not change anything. This is an expected safe failure, not a reason to bypass the check.
7. **Create a reviewed image version.** In Admin Image Release Readiness, the new **Create reviewed image version** button appears for current image evidence. After successful verification, expect the confirmation: image bytes copied and SHA-256 verified. The private version ledger records one immutable version with an approved-copy bucket object keyed by the digest. No payment or public release occurs.
8. **Revocation test.** Use **Revoke current image version**, enter a 10+ character reason, submit and verify the private revocation ledger records it. Repeating revocation must not overwrite/remove the first entry. Any photo edit, new evidence, or approval change must revoke old versions automatically; an old version cannot be revived.
9. **Public route remains blocked.** Repeat step 1 even after successful private image version creation. Expected **404**, because `apex_internal.private_release_gate.enabled=false` and `apex_internal.private_media_delivery_gate_v1.enabled=false`. Both are hard-disabled by database CHECK constraints; no one should alter them just to force a production test.

## Automated positive delivery and negative security tests

The GitHub **Apex quality checks** workflow runs ESLint, Next/TypeScript, Node tests, Deno Edge typecheck, a production build and **disposable PostgreSQL** tests. The media integration fixture deliberately creates a synthetic product, admin-review proof, supplier/product release authorizations, private image version, and (inside a rolled-back transaction only) temporarily enables both gates. It must return the correct immutable digest without revealing the source path, then deny delivery and append a permanent revocation after changing the image. Anonymous access to the privileged RPC must be rejected. The full payout-RLS workflow continues independently.

`deno check supabase/functions/apex-media-v1/index.ts` proves Edge TypeScript validity; no physical device test or synthetic database fixture is allowed to create hosted release evidence. Test the live endpoint with direct GET and no browser cache; all media responses have `no-store`.

## Activation gate / remaining non-code dependencies

The worker and UI can be deployed **with both gates OFF** and zero approved product media. Production image display only becomes eligible after independent seller/product and actual photograph/use-rights review, current authorization, verified copy, revocation and cache tests, and a separately reviewed migration for the hard-OFF global and media-delivery gates. **Do not confuse deploy READY with public images approved.**

Keep customer checkout, BTCPay, payment settlement, supplier payouts and shipping under Tracks 2 and 3. Image approval does not enable sales. Record mobile device/browser screenshots and failures separately; no unperformed manual device UAT is claimed here.
